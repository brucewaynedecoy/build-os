# BuildOS Security

This document is for enterprise engineering reviewers and for BuildOS maintainers. It covers the npm package `build-os` from version `0.1.0`. It names every outside package whose code ships in the package, with its version, license, reason, and scan status, and every package used only to build and test BuildOS. It explains how the package is built and bundled, how to check a release (provenance, tarball digest, and SBOM), the checks that run before each release, how to roll back, the input limits and file safety rules of the CLI, the known limits, and how to report a vulnerability. A reviewer can make a decision from this document, the SBOM, and the npm provenance, without reading the code.

The rules behind this document are in PRD 20 BuildOS CLI and Distribution (`docs/prd/20-buildos-cli-and-distribution.md` in the BuildOS repository), sections Supply Chain and Release.

## Summary

- Requirement: Node.js 24 or newer. The package declares `"engines": { "node": ">=24.0.0" }`.
- No runtime `dependencies`. `npm install` and `npx` fetch only `build-os`. A user's machine never resolves a third-party package version.
- All program code is one esbuild bundle, `dist/buildos.js`. It holds BuildOS code, four outside npm packages for document conversion and the fit-gap workbook (`fflate` 0.8.3, `parse5` 8.1.1 with `entities` 9.0.0, and `unpdf` 2.1.0 with the pdf.js 6.4.299 build inside it, which inlines six more components), and ports of Go 1.24.1 standard library code and two Go modules (BSD-3-Clause). See [Bundled Runtime Code](#bundled-runtime-code).
- 50 more lockfile packages are build-time only: TypeScript, esbuild, the Node type definitions, and their 47 transitive packages. None of them ships. See [Build-Time Tools](#build-time-tools).
- Every lockfile package uses the MIT, Apache-2.0, or BSD-2-Clause license. The Go code is BSD-3-Clause, and pdf.js is Apache-2.0.
- The published package declares no lifecycle script (the release check refuses a tarball whose `package.json` has one) and has no dependencies, so installing it runs nothing. In this repository's build, CI, and release, every install uses `--ignore-scripts`, and `toolkits/buildos/.npmrc` sets `ignore-scripts=true`; that file does not reach a user's machine. One build-time package, `esbuild` 0.28.2, declares a script that never runs here, under a closed owner-approved exception. See [Install-Script Exception](#install-script-exception).
- Scans: `npm audit` and the OSV scan found no known vulnerability in any of the 54 lockfile packages on 2026-11-24. See [Scan Record](#scan-record).
- Each release is built on one reference build environment from a reviewed commit, and the reviewed tarball SHA-256 is committed before the release. The checked tarball and a CycloneDX SBOM are attached to a draft GitHub Release, which the maintainer reviews and publishes (immutable). The release workflow then stages that release asset on npm with provenance, through npm trusted publishing (no stored token), after a person approves the staging job in GitHub. The maintainer approves publication with npm two-factor authentication. See [How to Check a Release](#how-to-check-a-release) and [Release Checks](#release-checks).
- The CLI makes no network call. It starts one outside program, and only when the user chooses it: the public Make Docs CLI for the optional Make Docs setup. See [Started Programs](#started-programs).
- The package also carries the BuildOS project files that `buildos init` copies into a project: Markdown, YAML, and JSON files, project wrapper scripts, and agent skills. BuildOS runs none of them itself. See [Package Contents](#package-contents).
- Every file a command reads is untrusted and read with a size bound. Every write stays inside the project folder unless the user passes `--allow-outside-root`. See [Input Limits](#input-limits), [Read Safety](#read-safety), [Write Safety](#write-safety), and [Known Limits and Out of Scope](#known-limits-and-out-of-scope).

## How to Check a Release

These steps use the version `0.1.0` as the example. Use the version you install. They need Node.js 24 or newer and network access to the npm registry. The commands were checked with npm 11.19.1, the npm that comes with Node.js 24.22.3. `npm audit signatures` checks provenance attestations only with a current npm, so update npm first when your npm is older.

### 1. Check the registry signature and the provenance

npm checks signatures and provenance for installed packages, so install the package into an empty folder first:

```sh
mkdir buildos-check
cd buildos-check
npm init -y
npm install --ignore-scripts build-os@0.1.0
npm audit signatures
```

The output must say that the package has a verified registry signature and a verified attestation. A missing attestation means the version has no provenance: do not use it.

Then read the provenance statement:

```sh
npm view build-os@0.1.0 dist.attestations.provenance.predicateType
```

It prints `https://slsa.dev/provenance/v1`. The npm package page shows the same provenance: the source repository `github.com/brucewaynedecoy/build-os`, the workflow `.github/workflows/buildos-release.yml`, and the commit of the release tag `v0.1.0`. npm makes provenance only for a public repository; the release workflow stops before staging when the repository is not public.

### 2. Check the tarball digest

Download the published tarball and compute its SHA-256:

```sh
npm pack build-os@0.1.0
shasum -a 256 build-os-0.1.0.tgz
```

On Linux, `sha256sum build-os-0.1.0.tgz` gives the same value. On Windows, run `certutil -hashfile build-os-0.1.0.tgz SHA256` in Command Prompt.

The value must equal `tarball_sha256` in the entry for the tag `v0.1.0` in `toolkits/buildos/release-candidates.json` in the BuildOS repository, and the `SHA-256` hash of `metadata.component` in the SBOM. The entry also names the reviewed source commit and the exact build environment (runner image, Node.js, and npm versions). The release workflow stages that exact file (the tarball attached to the release), so the registry copy has the same bytes.

### 3. Read the SBOM

Each GitHub Release has the CycloneDX 1.5 SBOM as the file `buildos-<version>.cdx.json`, next to the tarball `build-os-<version>.tgz`, for example `buildos-0.1.0.cdx.json` on the release page for the tag `v0.1.0` (`https://github.com/brucewaynedecoy/build-os/releases/tag/v0.1.0`). How to read it:

- `metadata.component` is the package itself: `hashes` holds the tarball SHA-256, and the property `buildos:source_revision` holds the source commit.
- A component with scope `required` is code in the package. Its property `buildos:delivery` says how it ships: bundled into `dist/buildos.js`, or Go code ported to TypeScript and bundled (no Go code ships).
- A component with scope `excluded` is a lockfile package used only to build or test BuildOS. It is not in the package (CycloneDX: not part of the runtime).
- `unpdf` lists the pdf.js build inside it, and pdf.js lists the six components it inlines.
- npm packages carry npm's license data, SHA-512 hashes, and registry URLs.

To list the code in the package:

```sh
node -e 'const s=require("./buildos-0.1.0.cdx.json");for(const c of s.components)if(c.scope==="required")console.log(c.name,c.version)'
```

```text
entities 9.0.0
fflate 0.8.3
parse5 8.1.1
unpdf 2.1.0
Go standard library 1.24.1
golang.org/x/net v0.48.0
github.com/ledongthuc/pdf v0.0.0-20250511090121-5959a4027728
```

These are the rows of [Bundled npm Packages](#bundled-npm-packages) and [Other Bundled Code](#other-bundled-code). The release check compares values: it fails when an SBOM hash is not the lockfile's, or when a package's version or license differs between the SBOM, the lockfile, this document's tables, and `THIRD_PARTY_NOTICES.md` (see the SBOM row of [Release Gates](#release-gates)).

## Rollback by Version Pin

`buildos init` writes the BuildOS version into the project file `.os/manifest.json` (`buildos_version`). The project wrapper `.os/scripts/buildos` (`.os\scripts\buildos.cmd` on Windows) always runs the pinned version (pin first, owner decision of 2026-11-25). It reads the pin first. It uses an installed `buildos` only when it is an npm install of the pinned version: in the `node_modules` folder of the project folder or of a folder above it (for example the root folder of an npm workspace), or the first `buildos` on `PATH` (for example after `npm install -g`). It never starts a program to learn its version; it reads only the package's `package.json` to choose a candidate. In every other case it runs `npx -y --prefix <current folder> --workspaces=false build-os@<pinned version>`, so npm runs BuildOS in the current folder, also inside an npm workspace. On every start it sets `BUILDOS_REQUIRE_VERSION` to the pinned version, and the BuildOS program that starts stops itself when its own version (the one `buildos version` reports) is another one (exit 3, see [Project wrappers](#package-contents)). So roll back by setting `buildos_version` to an earlier exact version, for example `"0.1.0"`, and running the wrapper again. That is the only rollback step for the command: you do not need to change or remove a global install. When the skills differ between the two versions, also put back the earlier skills, in `.os/skills/` and in each copy that an agent app installed; from `0.2.0` to `0.1.0`, the user guide (chapter 4, "Roll back from 0.2.0 to 0.1.0") lists the steps. The wrapper accepts only an exact version, never a range or a tag such as `latest`.

A global install is used only when it is an npm install of exactly the pinned version; otherwise the wrapper fetches the pinned version. To use a global install again without `npx`, install the pinned version: `npm install -g build-os@0.1.0`.

A direct `npx` call names its version, for example `npx -y build-os@0.1.0 <command>`. npm then runs a copy that it takes as that version. npm can take a local install of `0.1.0+local` as `0.1.0`, because npm ignores build metadata when it compares versions. A direct call has no self-check. To get the same check as the wrapper, set the variable yourself: `BUILDOS_REQUIRE_VERSION=0.1.0 npx -y build-os@0.1.0 <command>`.

Rollback needs the earlier version to still be on the npm registry. A version that a release must not use is marked by the maintainer with `npm deprecate`; npm then prints the deprecation message on install, and an exactly pinned deprecated version still installs. npm does not promise that every version stays. Under the npm Unpublish Policy, an owner can unpublish a new package within 72 hours of publishing it, as long as no other package in the npm public registry depends on it; at any time, an owner can unpublish a package that no other package in the public registry depends on, that had fewer than 300 downloads in the last week, and that has a single owner or maintainer. An unpublished version no longer installs, the unpublish cannot be undone, and its version number can never be used again. The BuildOS maintainer deprecates and does not unpublish. Keep a copy of a tarball you must be able to reinstall (see the offline install in the user guide). `buildos update` and `buildos uninstall` are not part of this release.

## Release Checks

Every check is a script that also runs on a maintainer machine (`node scripts/release-gate.ts <gate>`; `node scripts/release-dry-run.ts` runs them in workflow order). The workflow `.github/workflows/buildos-release.yml` runs in three modes:

- **dry run**: a manual run with purpose `dry-run`, or a push to a `release-dry-run/` branch. It runs the `resolve` and `verify` jobs and stops there: it never stages or publishes. `verify` runs the candidate gates of [Release Gates](#release-gates) with an invented deny list, and reports the provenance preconditions (a public repository, the repository URL) as warnings instead of failures. A dry run does not exercise the real-list scan, the ruleset and environment checks, `attach`, the required reviewer's approval, the release-asset checks, or staging: a prepare run first exercises the real-list scan, the ruleset and environment checks of the `deny-list` job, and `attach`; a release run first exercises the required reviewer's approval, the release-asset checks, and staging. It can plant one failure (`tag`, `version`, `digest`, `eval`, `audit`, `osv`, or `deny-list`) to show that the check stops the flow.
- **prepare**: a manual run from the default branch with purpose `prepare` and the tag of a draft GitHub Release. It runs `resolve`, `verify`, and the real deny list, then `attach` puts the checked tarball and the SBOM on the draft.
- **release**: the maintainer publishes that draft. The `release: published` event runs `resolve`, `verify` (a fresh rebuild), and the real deny list, then `stage` stages the tarball from the release assets on npm.

A prepare or release run refuses a planted failure.

### Release Procedure

GitHub's procedure for an immutable release is: create the release as a draft, attach every asset to the draft, then publish it. After that, the release's tag and assets cannot change. The BuildOS procedure follows it:

1. The maintainer sets the version, makes a dry run on the reference runner, inspects its tarball, and commits the `reviewed` entry to `toolkits/buildos/release-candidates.json` (header of `scripts/release-candidate.ts`).
2. The maintainer creates the tag `v<version>` on that commit (on the default branch) and a draft GitHub Release for it, for example `gh release create v0.1.0 --draft --verify-tag --title "BuildOS 0.1.0" --notes-file toolkits/buildos/RELEASE_NOTES.md`.
3. The maintainer runs the workflow from the default branch: Actions > buildos-release > Run workflow, purpose `prepare`, tag `v0.1.0`, candidates `committed`, plant `none` (or `gh workflow run buildos-release.yml --ref main -f purpose=prepare -f tag=v0.1.0 -f candidates=committed -f plant=none`). Every gate runs, then the real deny list, then `attach`.
4. The maintainer reviews the draft: downloads `build-os-<version>.tgz` and `buildos-<version>.cdx.json` from it, checks that the tarball SHA-256 equals the reviewed entry, and reads the job summary. Then the maintainer publishes the draft. With release immutability on, its tag and assets are now fixed.
5. The release run starts. Its `verify` job rebuilds the tagged commit on the reference runner and must get the reviewed digest again. When it reaches `stage`, GitHub waits: a required reviewer of the environment `buildos-npm-stage` approves the job (Actions > the run > Review deployments > Approve and deploy). Only then does the job start and get its OIDC token.
6. The `stage` job checks the rulesets, downloads the tarball and the SBOM from the published release, checks both, and stages the tarball on npm. The maintainer approves the stage on npm with two-factor authentication, only after the recorded publication approval.

What this guarantees: the staged file is the release asset; its SHA-256 equals the reviewed entry in the ledger at the tagged commit, which trusted code reads from git; and a fresh build of the tagged commit in the release run gave the same SHA-256 (the reproducible build), so the asset is the code at the tag. The SBOM on the release records that SHA-256 and the reviewed source commit, which trusted code checked before it attached the file and checks again before staging: the published release must hold exactly the tarball and the SBOM, the SBOM must be valid CycloneDX 1.5 and must have the same bytes as the SBOM that the release run's own `verify` job generated from the tagged commit. The SBOM generation is deterministic on the reference build environment (the serial number comes from the tarball digest and the source commit, the time stamp from the commit time, and the npm version is fixed), so a replaced SBOM fails.

### Release Trust Boundary

Trust rule: write access to this repository is a release-trusted role. Anyone with write access can push a branch, change the workflow files on that branch, run workflows on it, and create tags and draft releases within the rulesets below. Grant write access only to a person you would trust to release. Untrusted contributions come through pull requests from forks: a workflow run from a fork gets no secret and a read-only token.

The candidate is the commit the release points at. A person who can push can write its code, its build scripts, its `package.json`, and its `.npmrc`, so the workflow gives no secret and no write or publish permission to a job that runs any of it. Every privileged job runs only release-control code from the trusted ref: the default-branch commit that `resolve` found (`trusted_sha`). It reads the candidate only as data: the ledger by commit and path with `git` (it must be a regular file, git mode `100644`, never a link), the candidate tree as files, and the tarball as bytes through a strict tar reader.

| Job | Permissions and secrets | Code it runs |
| --- | --- | --- |
| `resolve` | `contents: read`; no secret | Only the workflow's own shell script and `git`. It validates every event value (the tag must be `v` and an exact semver version, at most 128 characters, before any use), resolves one release commit (release: the event commit, which must equal `refs/tags/<tag>^{commit}`; prepare: the tag's commit, from a run on the default branch), checks that the commit is on the default branch, and records the default-branch head as the trusted commit. A release from a repository that is not public stops here, because npm makes provenance only for a public repository. Every later job checks out an exact SHA, never a name. |
| `verify` | `contents: read`; no secret | The candidate's build, tests, and gates (table below). The deny-list gate here uses an invented list. The tarball, build record, and SBOM are uploaded only when every gate passed, as `buildos-release-<run id>-<run attempt>`, for 1 day (prepare and release) or 3 days (a dry run). |
| `deny-list` (prepare, release) | `contents: read`, `actions: read`; the real list, as the environment secret `BUILDOS_DENY_LIST_ENV` of the environment `buildos-deny-list` | `scripts/release-github.ts` checks that the environment deploys only from the default branch and `v*` tags, and then, before the step that holds the secret, that the branch and tag rulesets are active (`release-github.ts rulesets`, below). `scripts/release-stage-check.ts digest` checks the tarball against the ledger at the release commit. `scripts/check-deny-list.mjs` scans the candidate tree and every file of the tarball. All from the trusted commit, Node built-in modules only, no `npm`, no build. |
| `attach` (prepare) | `contents: write` | `scripts/release-github.ts attach` from the trusted commit: finds the one draft release of the tag (no asset yet), checks the tarball against the ledger, checks that the SBOM records the tarball SHA-256 and the reviewed source commit, uploads both to that release ID, and checks that the release lists exactly those two files with their SHA-256 digests. |
| `stage` (release) | `contents: read`, `actions: read`, `id-token: write`; environment `buildos-npm-stage` | From the trusted commit: first `release-stage-check.ts precheck` (a public repository and the OIDC token request); then `release-github.ts environment` (the environment has a required reviewer, deploys only from `v*` tags, and the run's review history approves it); then `release-github.ts rulesets`; then `release-github.ts download-asset` (the release is published and immutable, has the tag, and holds exactly two assets, the tarball and the SBOM of the version, each uploaded and with GitHub's SHA-256 digest; it downloads both, from the API's direct response or from the storage host it redirects to, without sending the token there; each file's bytes must match GitHub's digest; the tarball must match the ledger at the release commit and the `verify` digest; the SBOM must record that tarball SHA-256 and the reviewed source commit, be valid against the CycloneDX 1.5 schema, and have the same SHA-256 as this run's `verify` SBOM); then `release-stage-check.ts publish`, which checks the tarball against the ledger and the `verify` digest, refuses a `package.json` with `publishConfig`, a top-level `tag`, `private`, a lifecycle script, or a dependency field, and runs `npm stage publish` (below). |
| `discard` (prepare, release, after a deny-list failure) | `actions: write` | `scripts/release-github.ts discard` from the trusted commit: deletes the artifact only when it belongs to this run and has this run attempt's name. |

The review boundary. The workflow file of a release run comes from the tagged commit, and the workflow file of a prepare run from the default branch, so the file itself is only as trusted as the default branch and the release tags. These owner settings make that enforceable: a branch ruleset on the default branch with required reviews and code-owner review for `.github/workflows/**`, the release scripts, and the ledger (`.github/CODEOWNERS`); a tag ruleset so that only the maintainer can create, move, or delete a `v*` tag; release immutability, so a published release's tag and assets cannot change; and a required reviewer on `buildos-npm-stage`, so a person approves each staging job in GitHub before it gets its OIDC token. The last line of defense is the maintainer's npm two-factor approval of the stage. The `stage` job checks the environment's protection through the GitHub API with `actions: read` and fails closed when it cannot read it or finds no required reviewer, no approval in this run, or other deployment refs. The `deny-list` and `stage` jobs (and the real-list job of `buildos-deny-list.yml`) also check the rulesets with the job token, which always has the Metadata read permission that GitHub's ruleset endpoints need: the effective active rules of the default branch (`GET /repos/{owner}/{repo}/rules/branches/{branch}`) must restrict deletion, block force pushes, require a pull request with at least one approval and code-owner review, and require the six CI checks of step 8 below; and an active tag ruleset that targets `refs/tags/v*` with no exclusion (`GET /repos/{owner}/{repo}/rulesets` and each ruleset by ID) must restrict creation, update, and deletion. A missing rule or an unreadable answer fails the job. What the job cannot check: who may bypass a ruleset (GitHub returns the bypass list only to a user with write access to the ruleset, which the job token is not), and whether the repository setting for release immutability is on (that endpoint needs the Administration permission, which a job token cannot have); the `stage` job checks instead that the release itself is immutable. Who holds write access and who may bypass rely on the owner settings below and on the npm two-factor approval.

Code-owner review protects the default branch only. On a writer's own branch, `.github/CODEOWNERS` constrains nothing: the writer can change any workflow there and run it. That run cannot reach the release secrets, because the environments give their secrets and the OIDC staging permission only to the default branch and `v*` tags, the tag ruleset lets only a bypass actor create or move a `v*` tag, and prepare runs only from the default branch.

### Release Gates

`verify` job, on the GitHub runner `ubuntu-24.04` with Node.js 24.22.3 and npm 11.19.1:

| Step | It fails when |
| --- | --- |
| Reference build environment | Node.js is not `v24.22.3`, npm is not `11.19.1`, the runner image is not `ubuntu24`, or the checkout is not the resolved commit. The same commit gives the same tarball bytes in this environment. |
| Dependency guard, before and after `npm ci --ignore-scripts` | See [CI Checks](#ci-checks): a runtime dependency, an install script outside the closed exception, a version that is not exact, or `ignore-scripts` not set. |
| Release candidates file | `release-candidates.json` is not well formed: schema version 2; each entry has exactly the fields kind, version, tag (`v<version>`), tarball name, tarball SHA-256, source commit, Node.js and npm versions, runner image, reviewer, review date, and review evidence; a tag and a digest appear once; and every committed entry is of kind `reviewed`. |
| Tag, version, and reviewed entry | The tag is not `v<package.json version>`; the ledger at HEAD, read from git, is not a regular file with mode `100644`; no entry exists for the tag, or (prepare and release) it is not a `reviewed` entry; the entry version differs; the checkout is not the resolved commit; the reviewed source commit is not an ancestor of the release commit, or their files differ anywhere except the ledger's bytes; the prerelease flag disagrees with the version; or (prepare and release) not the reference environment. |
| Release build and pack | The build sets the package version and the reviewed source commit, so `buildos version` and every JSON envelope report them. A build refuses a working tree with changes. In a dry run with a self entry this is build B, a second clean build checked against the entry made from build A. |
| Tarball digest | The rebuilt tarball SHA-256 is not the reviewed one. |
| Build identity | The packed CLI does not report the package version and the reviewed source commit. |
| Typecheck and tests | Any failure of strict `tsc`, the unit tests, or the golden suites, or a run that executed no test. |
| Golden parity from the installed tarball | The release-stamped tarball, installed offline, does not match every golden case. The comparison expects the release version and source commit where a golden holds the development identity (`dev`, `unknown`), and every other byte as captured. |
| Conversion eval | A run with no executed test, an eval report that does not name every file of the eval manifest, or any file below the gate in PRD 07 Intake and Conversion. |
| `npm audit` | `npm audit --audit-level=high --include=dev --json` reports a high or critical advisory, exits with a status the counts do not explain, cannot run, or prints a report the check cannot read. |
| OSV scan | `osv-scanner` 2.7.1 (downloaded, SHA-256 pinned) reports a finding with a score of 7.0 or more or with no valid score, or the scan did not complete. See [OSV Gate](#osv-gate). |
| Deny-list scanner (invented list) | A personal home-folder path, or a shipped file the scanner cannot fully read, in the repository tree or the tarball. It carries the planted failure in a dry run. The real list runs in the `deny-list` job. |
| SBOM | The CycloneDX SBOM is not valid against the official CycloneDX 1.5 JSON schema (kept in `scripts/schemas/cyclonedx-1.5/` with its source URL, tag, commit, license Apache-2.0, and SHA-256 in `SOURCES.json`; `scripts/json-schema.ts` validates it, with no new dependency), or its values disagree with the sources: each package's SHA-512 with the lockfile `integrity`, and each package's version and license across the SBOM, the lockfile, this document's Bundled npm Packages table and Lockfile Inventory (and the package counts in the Summary), and `THIRD_PARTY_NOTICES.md`; or the bundle (the esbuild metafile) disagrees with which packages are marked as shipped. |
| Provenance preconditions | (prepare and release) The repository is not public, or `package.json` `repository.url` is not the GitHub repository. A dry run reports these as warnings. The `stage` job checks them again, first, with the OIDC token request. |

A failing gate stops the job: nothing is uploaded and no later job runs. A deny-list failure prints each location as a file label and line (never the term) in the log and in the job summary.

`stage` job, the npm call: `npm stage publish <tarball> --provenance --access public --tag <latest or next> --registry https://registry.npmjs.org/ --ignore-scripts`, from an empty folder, with every `npm_config_*` value and any npm token removed from the environment and the user and global npmrc set to empty files. The dist-tag comes from the reviewed entry's version (`next` for a prerelease), computed by the trusted script; npm 11.19.1 lets CLI flags win over a packed `publishConfig`, and the tarball check refuses a `publishConfig` anyway. The flag names were checked against npm 11.19.1 (`npm stage publish --help` and its `lib/commands/publish.js`). npm trusted publishing gives the job a short-lived token, so no npm token is stored. A staged package is not public. The maintainer reviews it on npmjs.com (signed in: account settings > the Staged Packages tab) or with `npm stage list build-os`, `npm stage view <stage-id>`, and `npm stage download <stage-id>`, and approves it with npm two-factor authentication (`npm stage approve <stage-id>`, or Approve on that tab) only after the recorded publication approval, or rejects it.

Other rules: GitHub Actions are pinned to full commit SHAs; checkout keeps no credentials; event values reach a script only through `env:`, never as `${{ }}` text inside a script; the GitHub token reaches only the steps that call the GitHub API, through `env:`, never the command line; and no workflow uses `pull_request_target`.

### Owner Settings for Releases

These repository settings are part of the release security. No agent changes repository settings. The owner sets them in exactly this order, so that no secret exists while a ref that could receive it is unprotected: first the old repository secret goes, then the rulesets protect `main` and the `v*` tags, then the environments limit their refs, and only then does the environment secret go in, and after that npm trusted publishing. `test/release-workflow.test.ts` keeps this order. Paths are from GitHub's documentation (Managing environments for deployment; Creating rulesets for a repository; Available rules for rulesets; Preventing changes to your releases; Configuring private vulnerability reporting; REST API endpoints for rules), read on 2026-11-24.

Owner decision of 2026-11-25 (git history): the current repository keeps the old history and stays private for good, and a new repository `brucewaynedecoy/build-os` starts with one clean commit of the release tree. The history is not rewritten in place: after a force-push, GitHub can still serve the old commits by their hash. Steps 1 and 2 are on the current repository, and step 3 is on every existing clone. Every step from step 4 on, and every `gh` command below that names `brucewaynedecoy/build-os`, is on the new repository.

GitHub Free (pin-first final check, finding 4): a repository owned by a personal account on GitHub Free has rulesets and environments only when it is public. So the new repository gets no ruleset while it is private, and these steps protect it in another way: it stays private and empty until one push from a fresh folder, that push sends only `main`, the remote is checked to hold exactly one commit, one branch, and no tag, and the rulesets go on at once after it becomes public. A branch rule never stops a tag: an old tag that reaches the new repository would make the archive history public, so no clone with old objects ever pushes to it.

### Sole Maintainer or Two Maintainers

Checked against GitHub's documentation on 2026-11-24. GitHub never lets the author of a pull request approve it, and "Require review from Code Owners" needs an approval from a code owner of each changed path. Every pattern in `.github/CODEOWNERS` names one person, the maintainer. So a second reviewer who is not a code owner cannot give the required code-owner approval for the maintainer's own pull request, for example the one that commits a ledger entry. A ruleset bypass list takes roles (Repository admin, Maintain, Write, or a custom role), teams, GitHub Apps, and Dependabot, not a single person.

Sole-maintainer route (the current setup):

- Branch ruleset `main`: Bypass list > Add bypass > the role Repository admin, then change "Always allow" to "For pull requests only". In a repository owned by a personal account, only the owner has the Repository admin role. With "For pull requests only", GitHub requires the owner to open a pull request for every change: a direct push, a force push, and a deletion of `main` are still refused. On the pull request, the owner can choose to bypass the rules and merge it. The required status checks still run on the pull request and their results show on it and in the audit log, but a bypass merge is not blocked by a missing approval or by a failing check: the owner's own care is the only review.
- Tag ruleset `release tags`: the Repository admin role, Always allow (tag rulesets have no pull request mode), so only the owner creates, moves, or deletes a `v*` tag.
- Environment `buildos-npm-stage`: leave Prevent self-review off. Then the owner, as the required reviewer, can approve the staging job of a run the owner started. With it on, nobody could approve it.
- What this protects: a writer other than the owner cannot merge a change to a code-owned path without the owner's approval, cannot create or move a release tag, cannot get the deny list or the staging permission from a branch, and cannot approve the staging job. A fork pull request gets no secret. Every release still needs the owner's GitHub approval of the staging job and the owner's npm two-factor approval of the stage.
- What it does not protect: there is no second person. A mistake or a compromise of the owner's GitHub account can change the workflows on `main` through a bypass merge, tag a release, and approve the staging job; only the npm two-factor approval, which needs the owner's second factor, stands after that.

Two-maintainer route (the alternative): give a second person write access and add them as a second code owner on every line of `.github/CODEOWNERS` (for example `/.github/ @brucewaynedecoy @second-maintainer`; the test then needs the same list on every line). Remove the bypass actor from the branch ruleset, so each person's pull request needs the other's approval and passing checks. Add the second person as a required reviewer of `buildos-npm-stage` and turn Prevent self-review on, so the person who starts a release cannot approve its staging job. The tag ruleset keeps the Repository admin bypass (in a personal-account repository, only the owner), so the owner still creates the release tags. Under the trust rule above, the second person is release-trusted.

## Admission Rules

BuildOS uses Node built-in modules first. An outside package is allowed only when Node cannot do the job, and only when it meets every rule below (PRD 20 Supply Chain).

1. It is widely used and actively maintained.
2. Its license is MIT, Apache-2.0, BSD, or ISC.
3. It has few or no dependencies of its own.
4. It is pinned to an exact version and recorded in the lockfile.
5. It has no install scripts. CI installs with `--ignore-scripts`.
6. `npm audit` and an OSV scan pass with no high or critical findings.

PRD 20 also names the build tools: TypeScript compiled with `tsc`, tests with Node's built-in test runner (`node:test` with `node:assert/strict`; no test framework package is installed), and the bundle with esbuild.

On 2026-11-23 the owner replaced Vitest with `node:test`. Vitest's dependency tree held 12 MPL-2.0 `lightningcss` packages, which rule 2 does not allow. This removed 67 lockfile packages.

## Bundling

esbuild bundles all runtime code, including the outside packages, into `dist/buildos.js`. The published `package.json` has no `dependencies`, `optionalDependencies`, `peerDependencies`, or `bundleDependencies`, so a user's machine never resolves a new third-party version. A fixed upstream package reaches users only through a rebuilt and republished BuildOS release.

The build is reproducible: esbuild always runs from the package root, so no path of the build machine enters the bundle; no clock value enters the build; and `npm pack` writes fixed file times. CI builds the package twice from an empty `dist/` on macOS, Linux, and Windows and requires the same SHA-256 (`scripts/reproducible-pack.ts`). Byte identity is claimed for the reference build environment only, because gzip output and file modes can differ between systems.

The bundle carries the license notices of bundled code as esbuild legal comments, and `THIRD_PARTY_NOTICES.md` holds every license text.

Project wrappers: `.os/scripts/` holds the wrappers `buildos`, `buildos-intake`, `buildos-discovery`, and `buildos-design`, each as `sh` and `.cmd`, and their helpers `pinned-version.cjs` and `node-required.txt`. A wrapper only finds BuildOS, and always the version pinned in `.os/manifest.json` (pin first): an npm install of that version, else `npx -y build-os@<version>`, else one plain message that Node.js 24 or newer is needed (exit 127). The wrapper never starts a program to learn its version (W1 R7 P8 pin-first review round 1). It reads `package.json` files only, to choose a candidate: first `node_modules/build-os` in the project folder and in each folder above it, then in npm's local project folder (the first folder up from the current folder with a `package.json` file or a `node_modules` folder; a file named `node_modules` does not count) and in each folder above it, as Node.js looks for a package (W1 R7 P8 pin-first final check, finding 1: npm hoists a workspace install to the workspace root), and only when none counts, the first `buildos` on `PATH` that is not a BuildOS project wrapper. To tell a wrapper, the helper reads at most the first 1,024 bytes of a `PATH` candidate. On macOS and Linux that `buildos` counts only when its real path (all links followed) is the `buildos` bin file of the nearest `package.json` above it. On Windows it counts only when it is an npm `.cmd` shim with the package next to it (`node_modules\build-os`, or the package folder of a `node_modules\.bin` folder); the shim itself never runs. The `package.json` must be a regular file (no link), at most 256 KiB, strict JSON, with the name `build-os` and exactly the pinned version (any version for a `dev` pin), and its `buildos` bin file must be a readable regular file inside the package and not inside a `node_modules` folder below it. The wrapper then runs that bin file as `node <bin file> <arguments>`, with the same Node.js that ran the helper and in the same working folder. A pnpm, yarn, or Volta shim, a hand-made script, and a file that cannot be read do not count: the pinned version runs through `npx`. A `dev` pin has no published version: with no install that counts, it stops with a message that names the two ways that work (exit 3). The `sh` wrapper starts `node` and `npx` by their path on `PATH`, never by bare name, with a leading `./` for a relative `PATH` entry, so a folder name that starts with `-` is never read as an option (W1 R7 P8 pin-first review round 2, finding 1).

The program checks itself (W1 R7 P8 pin-first review round 2). On every start (a local install, a `buildos` on `PATH`, or `npx`), the wrapper sets `BUILDOS_REQUIRE_VERSION` to the pinned version (or `dev`). The BuildOS program reads it first, before any command code, any output, and any file access, in `buildos` and in the legacy-name entry files alike (`src/cli/required-version.ts`). Just before that check, the program checks its own Node.js version (W1 R7 P8 pin-first final check, finding 3: a project can hold an older `node_modules/.bin/node`, and `npx` can start BuildOS with it): below 24, nothing on stdout, one plain message on stderr that names the needed and the found version, and exit code 3 (with `--json`, the failure envelope with diagnostic code `node_version`). The bundle parses and runs that far on Node.js 20 (checked with Node.js 20.18.0). When it is set, not empty, and not exactly the program's own build identity (the version `buildos version` reports: a release version or `dev`), the program stops: nothing on stdout, one plain message on stderr that names the required version, the version that started, and the two fixes (fix the install, then run the project wrapper again; or set the version in `.os/manifest.json`), and exit code 3. With `--json` on the command line, the refusal is the JSON failure envelope on stdout instead (diagnostic code `version_mismatch`). There is no fallback after a refusal. The program then removes the variable from its own environment, so a program that it starts (Make Docs, a nested tool) does not get it. An unset or empty variable means no check, so a direct `buildos` run is unchanged. The `package.json` read above only chooses a candidate; this check is what makes sure that a command runs only at the pinned version.

The wrapper runs `npx` with `npm_config_bin_links=true`, so npm makes the bin link of a package it installs into its cache, and with `--prefix <current folder> --workspaces=false`, so npm does not change to an npm workspace folder above the current folder. On every system, `pinned-version.cjs` starts `npx` (W1 R7 P8 pin-first final check, finding 5). It keeps the caller's own bin-links settings, in any case and spelling, in `BUILDOS_SAVED_<name>` variables and sets `BUILDOS_NPM_BIN_LINKS_OVERRIDE=1`; the BuildOS program puts the caller's settings back, together with the removal of `BUILDOS_REQUIRE_VERSION`, before it starts any other program. The helper applies the manifest contract of PRD 20 (shared with `src/core/init/manifest.ts` and tested against the same table, `test/fixtures/manifest-contract.json`), so only an exact semver 2.0.0 version with no build metadata and each number at most 9007199254740991 (the largest that npm reads as a version, not as a dist-tag) reaches the `npx` command line, and the `sh` wrapper checks the version's characters again. It reads the manifest as `buildos init` does: a regular file at the name only (a link is not followed), opened once, checked against the entry at the name, and read with a bound, so a file over 64 KiB is refused without being read. The wrappers skip every BuildOS project wrapper on `PATH` (the Go-era one too); never run a `buildos` from the current folder on Windows unless `PATH` names it (the `.cmd` wrapper also sets `NoDefaultCurrentDirectoryInExePath`); stop a chain of wrappers that comes back to them (`BUILDOS_WRAPPER_ACTIVE`, which the BuildOS program clears when it starts, so a program it starts can call a wrapper again); and turn delayed expansion off. The `.cmd` wrapper passes its arguments to the helper without `call`, so Command Prompt reads them once, and the helper starts the chosen program itself with the same console and exit code: `buildos` or `npx` as a `.cmd` file through `cmd.exe /d /v:off /s /c` with each argument quoted and every Command Prompt special character escaped twice (as cross-spawn does for npm's `.cmd` shims), any other program directly. No path goes back to Command Prompt as text, so a folder name in any language reaches the program whatever the console code page. `test/wrappers.test.ts` runs every wrapper with a `PATH` that holds only stubs and fixture npm packages, with recorder programs that check the exact argument list and that a program that must not run never starts, also from folders whose names are not ASCII or hold `!` or `%TEMP%`, from a quoted Windows `PATH` entry with a `;` in it, and under `dash` when the system has it. See [Known Limits and Out of Scope](#known-limits-and-out-of-scope) for the Windows limits.

Threat model of the wrappers. The pin gives a repeatable version and a rollback path. It does not defend against a hostile program named `buildos`, `build-os`, `npx`, or `node` on `PATH`, or against a hostile `node_modules` folder: a person who controls those controls the run already. npm itself decides which copy it starts for the `npx` fallback, and it can start a copy that the wrapper did not choose (for example a local install of `<pin>+local`, which npm takes as `<pin>`, or a copy with no bin link, after which npm starts the `bin` named after the package, `build-os`, by name from `PATH`). When that copy is BuildOS at another version, it stops itself through `BUILDOS_REQUIRE_VERSION`. A program that is not BuildOS and ignores the variable is outside what the wrapper can check. `test/package.test.ts` shows these cases with real npm 11: with the pinned version installed with `--no-bin-links`, `npx` alone runs a planted `build-os` from `PATH`, and the project wrapper does not; and a local install of `<pin>+local` that `npx` starts refuses itself. The local lookup takes any `node_modules/build-os` in the project folder or in a folder above it that passes the package test, as Node.js would find it; there is no extra package marker, because no BuildOS release exists without the self-check (nothing is published before `0.1.0`), so every BuildOS release that the lookup can find checks its own version. The helper compares package folders by name, and on Windows it compares paths without case, also on a folder that is case-sensitive; with the self-check, such a mix-up can choose a wrong candidate but cannot run another BuildOS version.

- No shell runs on macOS or Linux. On Windows, a `.cmd` or `.bat` program runs through `cmd.exe /d /s /c` with every argument quoted, and an argument with `%`, `!`, a quote, or a line break is refused before anything starts.
- The program gets no input (`stdin` is closed) and a 10-minute limit. Its output is read, not shown, except the first line of a Make Docs error.
- BuildOS never writes a Make Docs-owned file (`docs/`, `.make-docs/`) itself. A Make Docs failure leaves BuildOS set up and shows the exact retry command.
- Tests never run the real Make Docs. The CI job `make-docs-contract` runs the real Make Docs at both bounds of the pinned range in a temporary folder and Make Docs home.

## Install-Script Exception

PRD 20 Supply Chain rule 5 says that no package may declare an install script. The rule has one closed exception, which the owner approved on 2026-11-23 on the condition that it does not become a precedent.

The exception: exactly one package, `esbuild` 0.28.2 (the exact version in `package-lock.json`), may declare an install script, and only its `postinstall` script (`node install.js`). esbuild declares that script to check its platform binary.

Why it is safe:

- The script never runs. Every install uses `--ignore-scripts`, and `toolkits/buildos/.npmrc` sets `ignore-scripts=true`.
- esbuild works without the script. Its binary comes from an `@esbuild/*` platform package, which has no script.
- esbuild is a build-time tool only. It is never bundled or shipped. The published package holds only the files in [Package Contents](#package-contents).

How CI enforces it: `scripts/dependency-policy.ts` holds an allow-list with exactly one entry: the name `esbuild`, the version `0.28.2`, the script `postinstall`, and the command `node install.js`. `scripts/check-dependencies.ts` runs before `npm ci`, and again with `--installed` after `npm ci --ignore-scripts` and before every step that uses `node_modules`. The guard fails when:

- any other lockfile package has `hasInstallScript`, or any other installed `package.json` declares an install lifecycle script. The install lifecycle scripts are every script that `npm install` or `npm ci` can run: `preinstall`, `install`, `postinstall`, `prepublish`, `preprepare`, `prepare`, `postprepare`, `predependencies`, `dependencies`, and `postdependencies`. An installed package with a `binding.gyp` file and no `preinstall` or `install` script counts as declaring `install`, because npm runs `node-gyp rebuild` for it;
- the installed esbuild 0.28.2 declares any of those scripts other than `postinstall`, or its `postinstall` runs a command other than `node install.js`;
- `package.json` itself declares any of those scripts, sets `"gypfile": true`, or declares `workspaces`, or the package root has a `binding.gyp` file (npm would run `node-gyp rebuild` for the root as an implicit `install`; `"gypfile": false` does not excuse it), or the lockfile root entry has `hasInstallScript`. BuildOS may declare none of them. Both guard modes check the root;
- any `esbuild` copy in the lockfile, or the installed esbuild, has a version other than the allowed one;
- the allow-list holds more or fewer than one entry, or names a package that is not in the lockfile;
- `.npmrc` is missing, or does not set `ignore-scripts=true` exactly once, at top level (before any INI `[section]`), with no other spelling of the key;
- npm itself, run from `toolkits/buildos/` with an empty user config, does not report `ignore-scripts` as `true`. This catches an `npm_config_ignore_scripts` environment override too.

`test/supply-chain.test.ts` proves each failure case and the pass case.

Changes: to add a package to the exception, or to change the esbuild version, the owner must make a new decision, and PRD 20 must record it. Agents may not extend the exception. An esbuild upgrade therefore needs an owner decision before the allow-list changes. Each release checks again whether the exception is still needed (see [Release Checks](#release-checks)).

### OSV Gate

The OSV job downloads the `osv-scanner` 2.7.1 Linux binary from the GitHub release and checks it against a pinned SHA-256 before it runs. It does not use the `osv-scanner-action` container, because that container is pulled by a moving tag and hides the scanner exit code.

The scanner exit code is the only proof that the scan completed. When the scanner cannot reach the OSV API, it exits 127 and writes `{"results": []}`, the same file as a clean scan. So `scripts/osv-gate.ts` takes the exit code and fails closed:

| Scanner exit code | Output | Gate |
| --- | --- | --- |
| `0` (clean) | parses, no findings | pass |
| `1` (findings) | parses, at least one finding | fail when any finding scores 7.0 or more or has no valid score; pass when all score below 7.0. A valid score is a CVSS score as CVSS writes it: `0.0` to `10.0` with at most one decimal place, and no sign, leading zero, space, exponent, or other text. So `6.99`, `07.0`, and `7e0` count as no score and fail |
| `0` or `1` | missing, unreadable, not JSON, no `results` array, or findings that disagree with the exit code | fail |
| `127` (general error, such as an unreachable API), `128` (no packages found), any other code, or no code | any | fail |

`test/osv-gate.test.ts` checks each row with real, trimmed `osv-scanner` 2.7.1 outputs in `test/fixtures/osv/`: findings above the threshold fail, findings below it pass, an unreachable API (exit 127, empty results) fails, and a clean scan passes. The OSV job runs this test as a self-check before the real scan. The release workflow uses the same gate.

## Client-Name Deny-List Check

BuildOS files must never name a client. `scripts/check-deny-list.mjs` fails when a file names a client on the maintained deny list. The list itself names clients, so it is never committed, shipped, written to a file, or printed. This document names no client and no term on the list.

- Source: the environment variable `BUILDOS_DENY_LIST` (one term per line, or comma separated; each term at least 3 characters). In CI and in the release workflow it comes from the environment secret `BUILDOS_DENY_LIST_ENV` of the GitHub environment `buildos-deny-list`, whose deployment refs are the default branch and the `v*` tags, and it is passed only to the one step that runs the check. No repository or organization secret has that name, so none can stand in for it when the environment has no secret; the job then fails closed, and the scanner's message names the environment and the secret. Before the scan, the job checks through the GitHub API that the environment deploys from exactly the default branch and `v*` tags. For local use, `--list-file <path>` reads a file that must be outside the scanned folder.
- No list: exit 2, "deny list not provided" (fail closed). An empty secret counts as no list. Outside CI only, `--allow-missing` skips the check with a notice; with `CI` or `GITHUB_ACTIONS` set, a missing list always fails.
- Scan set: every file git tracks or would track in the repository (tracked files and untracked files that `.gitignore` does not exclude; never `.git/`), so `system/`, `docs/`, and every test fixture; plus either every file inside a built npm tarball (`--tarball <file>`), read from the tarball as data and printed as `[tarball]/<path in the package>`, or (local use) every file that `npm pack --dry-run` lists for the package (`--pack`), including the built `dist/system/`. CI and the release workflow use `--tarball`, so npm never runs in the scanned folder. Each package file is opened by its own disk path, kept apart from the path the check prints, so a package folder on another drive (such as a staged package in the Windows temporary folder) is read too. With `--pack` or `--tarball`, the check fails when a listed package file cannot be read or when the list is empty, and the summary says `<n> of <m> package files read`; a package file outside `--root` is printed as `[package]/<path in the package>`.
- Matching: case-insensitive substring after Unicode NFKC folding, with each run of white space read as one space, so a term split across lines still matches. Cross-line matching works at any file size: the text is folded in windows that overlap by more than the longest term. Substring rather than whole word, so a term inside an identifier, a path, or a URL still matches; a longer word that holds a term is a false positive that the maintainer rewords. File, folder, and archive member names are checked.
- File types: ZIP-based files (`.docx`, `.xlsx`, `.pptx`, `.zip`, and any file with a ZIP header) are opened with Node's built-in `zlib` (stored and deflated members; an encrypted or ZIP64 archive counts as not fully read), and each member is checked (three levels deep, 256 MiB per member). The archive comment, each member comment, and each central and local extra field are read too (as raw bytes, below), and never printed. An XML file or member (an XML name such as `.xml` or `.rels`, or a file that starts with an XML declaration) is read in its declared encoding: a byte order mark (UTF-8, UTF-16LE, UTF-16BE), UTF-16 found from a leading `<` with a zero byte, or the declaration's `encoding`, else UTF-8. It is checked as full text and as visible text. Visible text joins the actual text nodes and ignores the markup and the formatting white space between elements: in an Office or OpenDocument part, the characters inside text runs (`w:t`, `a:t`, `t` in `.xlsx` shared strings and inline strings, ODF paragraphs) of each paragraph, cell, row, or string item make one line, so a term split across runs and across indentation still matches; in any other XML, text nodes join when one element holds the other or both sit in an element with text of its own. Office document properties (`docProps/*.xml`) are members and are read this way. PDF: every Flate stream is inflated (XMP metadata and object streams), and every string object is decoded (literal strings with their escapes, hex strings, UTF-16BE with a byte order mark), which is where the document information (Title, Author, and the rest) is kept. PNG: `tEXt`, `zTXt` (inflated), and `iTXt` (UTF-8, inflated when compressed) chunks are decoded. Text with a UTF-16 byte order mark is decoded as text. Any other binary file, JPEG included, is checked as raw bytes: UTF-8, Latin-1, and UTF-16LE and UTF-16BE at both byte alignments, which covers JPEG `COM`, EXIF (including its UTF-16 fields), and XMP segments.
- Encoded forms: every text the check reads, in any file type (XML attribute values and text nodes included, so an `.xlsx` sheet name in `xl/workbook.xml` and HTML-escaped text inside a CSV field are covered), is checked raw, then once with XML and HTML character references decoded (the named references `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;`, and `&nbsp;`, and decimal and hex numeric references), then once percent-decoded (`%XX` runs read as UTF-8, `+` as a space, as in a URL query). The term and the text are folded the same way. A decoded line break becomes a space, so line numbers stay; a match only in a decoded form prints `:decoded <line>` or `:url-decoded <line>`. File, folder, and member names and every printed path part are checked and redacted in the same decoded forms.
- Home-folder paths: every file, member, and name is also checked for a path inside a personal home folder (`/Users/<name>/`, `/home/<name>/`, `<drive>:\Users\<name>\`, or a UNC profile `\\<server>\Users\<name>\` or `\\<server>\<drive>$\Users\<name>\`, with escaped backslashes or slashes too), such as a build path that a compiled binary keeps. The profile name is read as one whole path component in any script (so a name that only starts with an allowed word, or that starts with a non-ASCII letter, is still found); a Windows name with spaces is read up to the next separator. Placeholders that start with `<`, `$`, `%`, `{`, or `.` are not names. A few generic names are allowed: GitHub runner accounts (`runner`, `runneradmin`, `RUNNER~1`), shared folders (`Shared`, `Public`, `Default`), and documentation placeholders (`me`, `user`, `username`, `you`, `name`, `example`, `someone`). One dependency path is allowed: the bundled PDF reader (unpdf 2.1.0's pdf.js build, in `dist/buildos.js`) defines a simulated environment for its WebAssembly image decoder with a fixed `HOME` value. It is allowed only as that exact text, only in the package file `dist/buildos.js`; the same text in any other file, or a changed text, fails, and `test/deny-list.test.ts` fails when the dependency changes or drops it. A match fails the check and prints `deny-list: home folder path in <path>:<line>`; the folder name is never printed. This check needs no list, but it runs inside the same script, so it runs wherever the deny-list check runs.
- No silent skips: every file or archive member that is not fully read is counted in the summary by reason: a file over 256 MiB, an archive member over the member limit, an archive nested more than three levels deep, an archive that cannot be opened, a binary file read as raw bytes only, or a path that is not a regular file. Such a file or member in `system/` or in the package file list fails the check and is named (through the same redaction). A path that git lists but that is missing from the working tree is counted as missing.
- Output: `deny-list: match in <path>:<line>` (or `<path>!<member>:<line>` inside an archive, `:text <n>` for the nth paragraph of visible text, `:name` for a name), and a count summary. One function prints every location: each part of every path, archive members and nested archives included, is shown as `[name on the deny list]` when it matches a term and as `[home folder name]` when it is a personal home folder name. The matched term, the line text, an unknown command-line argument, and error messages are never printed; an internal error, including an uncaught error or a rejected promise, prints only its kind, and debug options such as `NODE_DEBUG` or `--trace-uncaught` add no term or stack to the output (`test/deny-list.test.ts`). The list is removed from the environment of the `git` and `npm` processes the script starts. GitHub's secret masking is a second guard, not the only one.
- Where it runs: `.github/workflows/buildos-deny-list.yml`, on every push and pull request with no path filter. The job "Deny list (invented list, every push and pull request)" runs everywhere, forks included, with no secret: the self-test `test/deny-list.test.ts` (invented terms only), a build and pack (`scripts/pack-for-scan.ts`), and the scanner over the repository and the tarball with an invented list. It is the check to require on pull requests. The job "Deny list (real list, default branch only)" runs the real list only on pushes to the default branch (and runs started there by hand), in the environment `buildos-deny-list`; it runs only the environment check and the scanner, with Node built-in modules, over the checkout and the tarball from the first job. It is skipped on pull requests, so it must not be a required check (GitHub counts a skipped required check as passing). Every other ref gets a notice that the real list runs after merge and in the release workflow. The release workflow runs it again in prepare and release runs, from the default branch's scanner, on the candidate tree and the reviewed tarball, before attaching and before staging. A maintainer can run it before pushing: `node scripts/check-deny-list.mjs --root ../.. --pack . --list-file <file outside the repository>`. A run on the default branch without the secret fails.
- What it does not find: see [Known Limits and Out of Scope](#known-limits-and-out-of-scope).

## Input Limits

### Intake Input Limits

Every file `buildos intake convert` reads is untrusted. Each limit below is far above what a real office document, web page, or PDF needs. A source over a limit fails with exit 1 and `buildos-intake: error: <format>: <what> exceeds the BuildOS input limit (<limit>)`, in the same class as Go's "not a valid zip file" or "XML syntax error" failures, before any side artifact or twin is written (the whole source is read and checked first). The values are the constants in `src/core/intake/limits.ts`. `test/intake-hostile.test.ts` runs each hostile case (ZIP bombs, unsafe entry names, too many entries, billion laughs, an external entity, deep XML, HTML 100,000 levels deep, a huge sparse XLSX cell reference, too many cells, and too many PDF pages) through the real CLI with a 256 MiB heap and checks the clean failure, the time budget, a peak resident memory under 1 GiB, and that nothing is written in or beside the project. Production-scale cases run at or past each real limit: 2,000,000 attributes on one element, a 20 MiB attribute, 1,080,000 attributes and 1,000,001 sibling elements in a parsed part, 9,000 overlapping ZIP entries, 2,000,001 shared strings, 65 MiB of shared string text, one 1 MiB shared string in 200 cells, and one PDF page with 70 million characters. One known limit is in pdf.js (see [Known Limits and Out of Scope](#known-limits-and-out-of-scope)).

| Input | Limit | How it is enforced |
| --- | --- | --- |
| ZIP entries (DOCX, XLSX) | 10,000 entries | Counted from the central directory before any entry is read |
| ZIP entry names | No `..` part, absolute path, drive letter, backslash, or NUL | Every name is checked from the central directory; one unsafe name refuses the archive (`zip: insecure file path "<name>"`) |
| One ZIP entry, expanded | 256 MiB | Checked on the declared size first, then on the real inflated output, which also may not pass the declared size (`zip: not a valid zip file`, as Go) |
| All ZIP entries read, expanded | 512 MiB | Summed over the entries the converter reads; only the parts it uses are inflated |
| ZIP compression ratio | 250 to 1, for an entry over 1 MiB | Declared size over compressed size, before inflating |
| ZIP integrity | Go's CRC-32 check | `zip: checksum error`, as Go |
| XML nesting | 1,000 open elements | In the decoder, as each start tag is read |
| XML tree | 1,000,000 elements, attributes, and text runs | For the parts parsed into a tree (workbook, relationships, numbering); attributes are charged as the decoder reads each one. DOCX bodies, worksheets, and shared strings are streamed |
| XML attributes | 10,000 per element, and 16 MiB of names and values per element | In the decoder, as each attribute is read, in every part |
| XML entities | Only `&lt;`, `&gt;`, `&amp;`, `&apos;`, `&quot;`, and character references | As Go: a DTD is skipped, its entities are never expanded, and no external entity is loaded |
| HTML nesting | 512 open elements | In the parse5 tree adapter, as each node is inserted, so parse5's own work stays bounded |
| HTML nodes | 2,000,000 | In the parse5 tree adapter |
| XLSX columns | 16,384 per row (Excel's own last column, `XFD`) | From the cell references, before the row is allocated |
| XLSX rows | 1,048,576 per sheet (Excel's own limit) | As rows are read |
| XLSX cells | 20,000,000 allocated per sheet | Sum of row widths; each row is written to the CSV as soon as it is read |
| XLSX shared strings | 2,000,000 strings, and 64 Mi characters in all | As each string and each text run is read |
| XLSX CSV twin | 128 MiB per sheet | As each row is written (a shared string can repeat in every cell) |
| PDF pages | 5,000 | From the document's page count, before any page is read |
| PDF text | 64 Mi characters | As text runs are read; a page stops being read once the budget is spent |
| PDF object nesting | 1,000 nested arrays and dictionaries | In the cross-reference checks (a port of Go's `pdf.NewReader` checks) |
| PDF `/Prev` sections | 1,000 | In the cross-reference checks; Go follows a `/Prev` loop forever |

### Validate Input Limits

`buildos validate` only reads. Every file it checks is untrusted. It reads each file through the filesystem port, once, from one open checked against the entry at the name and against its folder (`readFileLimited`, see [Read Safety](#read-safety)), with the bound below; a larger file is not read. It reads only regular files inside the project root. An entry at a checked name (a `.md` name under `playbooks/`, a `*playbook*.md` name in `.os/templates/`, the contract, the config, or a data file) that is a link, a pipe, a socket, or a device is never read and gives a finding. A link at any other name, also a folder link under `playbooks/`, is skipped: BuildOS never follows it, enters it, or looks through it to decide what it is. A folder link that leads out of the project is never read through. Text must be UTF-8 (one byte order mark at the start is ignored). Each of these cases, and each limit below, gives a finding (exit 4) or is skipped, never a crash or a read outside the project. The values are `VALIDATE_LIMITS` in `src/core/validate/validate.ts`, `YAML_MAX_DEPTH` in `yaml-subset.ts`, and `JSON_MAX_DEPTH` in `checks.ts`; `test/validate.test.ts` runs each hostile case (oversized files, YAML block and inline list nesting, a 100,000-level inline list, a 200,000-level JSON line, links in and out of the root, a pipe at a checked name, bytes that are not UTF-8, CRLF, byte order marks, deep folders, a findings flood, and one row with 10,001 bad references).

| Limit | Value | Checked |
| --- | --- | --- |
| Config contract and config file | 1 MiB each | Before the file is read |
| One scoped Markdown file | 4 MiB | Before the file is read |
| One entity data file | 128 MiB | Before the file is read |
| YAML nesting (config, frontmatter) | 64 levels, block levels and inline list levels together | As blocks and inline lists open |
| JSON nesting (one data line) | 512 levels | Before the line is parsed |
| Folder depth under `playbooks/` | 32 levels | As folders are listed |
| Markdown files checked | 10,000 | As files are listed |
| Findings reported | 10,000 | In the collector: no check builds more; every loop over values, lines, and entries under `playbooks/` stops once the budget is spent, and the walk under `playbooks/` stops; the one listing of `.os/templates/` (a single folder, not walked) is read whole and does not check the findings budget, and each matching name counts toward the 10,000-file limit (follow-up F-P7-05); the result says it stopped (`truncated`). Data file lines are made one at a time from the bounded text, never split into one array |

The removed Python validator read every file whole, followed links (also out of the project), and crashed on deep nesting and on bytes that are not UTF-8.

## Read Safety

### Size Bounds

Every file read in `src/core/**` has a size bound. The port's `readBytes` and `readText` take the bound as a required argument: they open the file once, check that the opened file is a regular file no larger than the bound (`fstat`), and read at most one byte more than the bound from that open, so a file that grows while it is read is refused too. A larger file throws `EFBIG` with the bound, no byte of it is kept, and the command fails with `read <path>: file too large: BuildOS reads at most <bound> from one such file` (exit 1 in the Go-shaped domains; a read diagnostic in `entities`). A folder fails as Go's read does. The bounds are `READ_LIMITS` in `src/core/shared/read-limits.ts`:

| Read | Bound | Read sites |
| --- | --- | --- |
| Data: a JSONL dataset, a JSON index, a consolidation manifest | 128 MiB | entities (graph load, index check and rebuild, consolidation datasets and manifest); discovery (playbook index, run and finding indexes); design (findings index, rollback compare) |
| Document read whole by discovery or design | 64 MiB | discovery evidence and raw finding text, raw finding reference; design qualification file and finding record |
| Make Docs design input | 4 MiB | design promotion (router, workflow, contract, template, prompt; legacy `docs/assets/` too) |
| Intake file | 512 MiB | intake convert sources (each file of an HTML folder too, also for its hash), converted twins read by `index references`, playbooks read by `index playbooks`, the previous references index. Each format's own limits then apply ([Intake Input Limits](#intake-input-limits)); `extract bulk` source files it hashes and converted files whose lines or CSV rows it counts |
| Skill-script command input (W1 R7 P9) | 128 MiB | `extract bulk` (the references index, review files, `.os/data/*.jsonl`, staged rows, the publication's data files, standard input of `replace-row` and `decide`; also `.os/config/instance.yaml` for the row checks, with `buildos validate`'s reader and config bound, and a lock file it finds, at most 4 KiB); `fitgap` (the frame, both models or CSV files, a prior fit-gap file, scored, target-only, findings, and to-do files, the merged JSON, the skill palette, the workbook it reads back, and each numbered `pkg-NN.json` in the packages folder it would delete, to confirm it is its own output, also in an authorized outside folder); `export azure-boards` (the manifest and the CSV it validates) |

The evidence copy of `discovery run` is a streaming copy (`openRead`, 8 MiB at a time, never held whole), so its memory is bounded; it has no size bound, as Go's `io.Copy`, because the user names the file and its bytes go only to a new file in the project. The audit of every read site is in the W1 R7 evidence report, section P7 Review Round 2.

### Contained Reads

A bounded content read (`readFileLimited`: `buildos validate`, the shared files and the manifest of `buildos init`, and the design inputs) is always contained, also with `--allow-outside-root`. It does the same folder checks as a write. It checks the folder's real path (inside the root), then takes the folder's identity (device and inode), looks at the entry at the name without following a link (`lstat`), and opens it with `O_NOFOLLOW`. After the open, the folder must still have the same real path, inside the root, and the same identity; the opened file must be a regular file with the identity the `lstat` saw; and the name must still be that file. Else the read is refused (exit 3, or an `outside_root` finding in `buildos validate`), and no byte of it is used. `test/fs-port.test.ts` swaps the folder for a link to an outside folder between the folder check and the open, through a test-only hook, and shows that the read is refused, also with `--allow-outside-root`. On Windows the same checks run (Node gives a folder's file ID through `stat`); the CI job runs the read tests that need no symlink.

### Skill-Script Commands

`buildos extract bulk`, `buildos fitgap`, and `buildos export azure-boards` (W1 R7 P9) replace three skill scripts that read and wrote any path. Each reads only inside the project folder (`--root`, default the current folder), with or without `--allow-outside-root`: a path the user names, a path a frame or a manifest names, every path the references index names, and every `--rows`, `--only`, and `--todos` pattern. Every read is a bounded content read through the root port's opened-file-checked reader (`readFileLimited`, review round 1, P9-R1-05; the checks in [Contained Reads](#contained-reads)); a link at the name is read only when it leads to a regular file inside the project. A pattern expands from its literal folder, however it is spelled (relative, absolute, or with `..`), and that folder and every match must be inside the project: a pattern outside it is refused (exit 3), never an empty match (P9-R1-02). A path the user types follows the shared layout rule of every domain (P9-R1-13). An absolute path the user types that spells the project folder another way (another letter case on a case-insensitive volume, `/var` for `/private/var` on macOS, or through a link to the project folder) is inside it when one of its existing folders is the project folder itself, compared by device and inode through every link (review round 2, P9-R2-10); the rest of the path is then read or written through the root port with the usual checks. A path outside, or a link that leads out, is refused (exit 3). Every JSON input nests at most 512 levels (the Azure Boards manifest and `--adapter-params` too, P9-R1-16), and standard input is bounded to 128 MiB (a larger one is exit 3).

Their writes are planned: every destination is checked before the first change (inside the project, or outside only for a `fitgap` or `export azure-boards` output with `--allow-outside-root`, also when a folder of the destination inside the project as spelled is a link that resolves outside it: the destination is then written as if its outside path had been named, through the port of its volume, and without the switch it is refused with the message that names the switch, review round 3, P9-F-08; its folder can take a new entry; no folder at a file's name; its size against the bound its reader uses). `fitgap` and `export azure-boards` never read a destination to write it (P9-R1-04): a new file is written whole and flushed under a private name in its folder (`.<name>.buildos-<random>.new`), an entry that is already at the destination is moved aside by a same-folder rename to a private backup name (`.<name>.buildos-<random>.backup`), and then the new file is renamed into place. A link at the written file itself is replaced, never followed: the link is what moves aside, so the file it names is never read or changed. A regular file that is replaced keeps its permission bits (the new file gets exactly them), and a destination that cannot be opened for writing (a read-only file; on Windows the read-only attribute) stops the command before the first change with exit 5, as the scripts' writes in place refused it (review round 2, P9-R2-06); a link at the destination is replaced and the new file gets the default mode. When a later step fails, each backup is renamed back (a link keeps its identity), and each new file is removed only while it is still the entry BuildOS wrote; a step that took effect before it reported a failure is undone too. After the last step the backups are removed. Every leftover is reported with its exact path (P9-R2-07): after a failed write, an earlier file still under its backup name (and that it must be renamed back), a new file or temporary file that could not be removed, or a folder that could not be removed, each in human output and in the JSON result (`not_restored`) and diagnostics, with exit 10 and `write_status` `partially_applied`; after a complete write, a backup that could not be deleted is named on stderr and in a JSON warning and `result.left_behind`, with exit 0 (the outputs are complete, and the backup is a hidden private name that no command reads). `fitgap packages` lists the destination folder itself, also an authorized one outside the project, and removes as steps of the same plan only the `pkg-*.json` files it can tell are its own earlier output (review round 2, P9-R2-02): a numbered name as it writes them (`pkg-01.json` and up), a regular file, and JSON with exactly the fields of a package. To tell, it reads each such numbered file once, at most 128 MiB, with no link followed, through the port of the destination (inside the project, or the authorized outside folder); this is the only read of a destination. Every other `pkg-*.json` (a user's own file, a hand-edited one, a link) is kept and named on stderr and in `result.kept`. Before any change, `fitgap packages` knows every package name the run writes; when a file it would keep is at one of those names (for example `pkg-01.json` with a grader's notes added), the run stops with exit 4, changes nothing, and names each such file with what to do (move or rename it, or choose another `--out` folder), so a kept file is never one the run then writes over (review round 3, P9-F-01). The scripts removed every `pkg-*.json` there (divergence SD-20). `extract bulk` plans every write of a command (the review, the staged files, the data files, and the folders it makes) and checks them all, then makes them in the script's order, each an atomic replace (P9-R1-10, P9-R1-11); a failure undoes the changes in reverse, each only while the entry is still the one it wrote (the earlier bytes, permission bits, or link are put back), and stops at the first step it cannot undo for sure, so what stays is what a crash at that point would leave: for `publish`, the publication intent in the review (written first) names the pending data files, and the next `publish` resumes it. A write that took effect before a later part of it failed (the folder flush after the rename) is undone too (review round 2, P9-R2-01); an earlier file put back whose save to disk is not certain is reported `unsure`, and the undo stops there, so the intent stays while any data file of the publication is not surely back. A resumed publication applies a file whose content hash is still the recorded one before it, skips a file that already has its recorded result, and checks the recorded rows against the config as it is then (P9-R2-04). A file that matches neither hash is read row by row and each row of the publication is looked up by the ID the intent gave it (review round 3, P9-F-02, divergence SD-22): all there, the file is skipped; none there (an updated row still with its staged base hash), the operations are applied once to the file as it is now; anything else stops the command before any write with exit 10 and the intent kept, naming the file and the row IDs, with steps that never write a row twice. So a retry never writes a row twice and never finishes a publication whose rows `buildos validate` would refuse; withdrawal by hand is offered only when every data file is exactly as it was before the publication started. A failed write that was undone reports `write_status` `not_requested` and exit 5; one that could not be undone names every remaining path, reports `partially_applied`, and exits 10. `extract bulk` checks every row a publication would write with `buildos validate`'s row checks and the project config before anything is written (P9-R1-01); it reads the config with `buildos validate`'s own reader and findings budget, so it builds the same config index as validate (review round 3, P9-F-05), and a config that validate cannot read as UTF-8 text stops it with validate's finding (P9-R2-11), also a `decide` that only withdraws approval (P9-F-06). It takes a lock file in `extractions/staging/` for the length of a command instead of the helper's `flock`. Only an entry already at the lock's name is another command's lock; any other failure to create it is a write error at the lock path (exit 5); a lock file that cannot be removed when the command ends is named, with exit 10 and `partially_applied`, also when the command's own writes completed, because it stops the next command (P9-R2-08). A crash between two renames of a `fitgap` or `export azure-boards` write can leave a `.buildos-*.new` or `.buildos-*.backup` file next to the output; the backup holds the earlier file. Divergences SD-04 to SD-22 in `test/golden/skills/divergences.json` list every difference from the scripts.

### Paths Outside the Project

The Go-shaped domains (intake, discovery, design, and the entity manifest) keep the read rule the owner approved in parity exceptions PE-010 and PE-012: a path the user names, or that an index names, may be outside the project root, as Go read it, through a read-only port bound to the volume; the size bound applies there too.

- Design inputs: `buildos design promote` reads each Make Docs design input, legacy ones too, through a port bound to the project root (`GoFiles.readContained`, `readFileLimited` with `followLinkInRoot`). The entry at the name is looked at without following it. A regular file is read with every check above. A link is read only when its real path is a regular file inside the root: the file at that real path is read with the same checks, and the link must still resolve to it after the read. A link that leads out of the root, or to a device, is refused (exit 3); a dangling link or a folder counts as a missing input. A file over 4 MiB stops the command with the size message (exit 1) and never falls back to a legacy body, and `--allow-outside-root` does not change these reads. The one exception is a write-destination case that an approved edge golden pins (`design-designs-link-outside-allowed`, PE-012): with the switch, when the designs folder itself is a link out of the root, the router `AGENTS.md` in it (a regular file, not a link) is read through that folder link, bounded (`GoFiles.readInWriteFolder`). A refused read never names the switch in its message.
- Entity graph: discovery and design load `.os/data/` through a port bound to the project root (`GoFiles.openEntityRoot`), in every mode, as `entities` does (PE-007): a data folder or dataset that leads out of the root is refused (exit 3). One narrow case keeps Go's read, because approved edge goldens pin it (PE-014: `discovery-runs-index-link-outside`, `design-index-link-outside`): the index the command replaces (`runs.jsonl` for a run, `findings.jsonl` for a finding or a promotion) may be a link at its own name to a file outside the root, in a folder inside the root; the command replaces that link with a regular file and never writes through it.
- HTML images (parity exception PE-018, approved 2026-11-24): an HTML document is untrusted, and Go read any path its `<img src>` named and copied the bytes into the project. `intake convert` reads a local image only through a port bound to an allowed folder: first the folder that holds the HTML file (for an HTML folder source, the selected folder), then the project root. The path must be inside that folder as spelled, and its real path after every link must be inside it too, so a link never leads the read out. Any other image (an absolute path or a `../` path outside both, or a link out of them) is not read; an image over 512 MiB is not read either. Each gets Go's `[Uncopied image: ...](...)` marker and one stderr line with the reason; the marker keeps the address as the document gives it, which is relative to the document, not to the converted file, and the warning says so; the command exits 0. The address is percent-decoded once before the containment check (`my%20image.png` names `my image.png`, and an encoded `..%2F` is refused like `../`); when no file has the decoded name, the address as written is tried, as Go read it; an address with an invalid escape is used as written; an address that decodes to a zero byte is not read. `--allow-outside-root` does not widen this. `http(s):`, `data:`, and `file://` sources are handled as in Go.

### Read-Back Sizes and Row Limits

A file BuildOS writes and later reads back is checked against its reader's bound before the first write; a larger result stops the command (exit 4, `file_too_large_to_read_back`, the dry run too) and writes nothing. The writers: the discovery runs and findings indexes (128 MiB), the raw findings, finding, and qualification records (64 MiB); the promotion's findings index (128 MiB) and finding record (64 MiB); the intake playbooks index (128 MiB, discovery reads it), references index (512 MiB), and converted twins (512 MiB); the entity datasets of a consolidation and the entity-resolution index (128 MiB, also the index a consolidation rebuilds, checked before the canonical write). Not checked, because BuildOS never reads them back: the run record `run.md`, copied evidence, side artifacts, the design file, and the `buildos init` package files (fixed package content and a small manifest).

JSONL row limits (parity exception PE-019): a reader that scans a file line by line cannot read a line of its limit or more, so each row a command writes is checked against the line limit of every reader of that file before the first write and before a dry run reports success; a longer row stops the command (exit 4, `row_too_long_to_read_back`) and writes nothing. The writers and limits: `discovery run discovery` (the new `.os/data/runs.jsonl` row) and `discovery qualify finding` (the new `.os/data/findings.jsonl` row), 64 KiB, because the next run, `qualify finding`, and `design promote` read these files with Go's 64 KiB `bufio.Scanner` token; `design promote finding`, every row of the rewritten `.os/data/findings.jsonl`, 64 KiB; `entities consolidate`, every row of the dataset it rewrites, 64 KiB for `runs.jsonl` and `findings.jsonl` and 16 MiB for any other governed dataset (the entity graph's line limit). `buildos extract bulk publish` (the port of the `buildos-bulk-extract` skill helper) applies the same limits before it publishes rows, and keeps each staged file under its 128 MiB read bound. No other command writes a JSONL file. The skill-script commands also check before the first write: the merged fit-gap JSON, packages, target index, and target CSV, the Azure Boards CSV, and the workbook (each 128 MiB, the bound their readers use).

## Write Safety

### The Filesystem Port

Every write goes through the filesystem port in `src/adapters/node-fs.ts`. Before a write, the port checks the target's folder by its real path (after every symlink) and refuses a target outside the root, a device, a special file, or a file descriptor (exit 3) in every domain, unless the command is given `--allow-outside-root` (intake, discovery, and design; it relaxes only that containment check for write destinations, never a device, special-file, or file-descriptor refusal, and never a content read). A symlink at the written file itself is replaced, never followed. Node has no `openat`, so the port cannot open a file relative to a folder it holds open. It does the strongest check Node allows:

- The in-place writer (intake twins, side artifacts, and indexes) opens the file with `O_NOFOLLOW` and never with `O_TRUNC`. An existing file is opened without `O_CREAT`; a new file is created with `O_CREAT` and `O_EXCL`. Without `--force`, `intake convert` tells the writer not to overwrite (W1 R7 P9 intake JSON final check, finding 1): the writer then never opens an entry at the name, and an `O_EXCL` create that meets a file is not tried again as an overwrite. So a twin or side artifact that another program makes after the command's existence check keeps its bytes, and the command stops with the `use --force` error (PE-010).
- After the open, the port checks the opened file with `fstat`: it must be a regular file with one hard link. Then it resolves the folder's real path again. The folder must have the same real path and the same device and inode as before the open, and must still be allowed (inside the root, or reached through a link with `--allow-outside-root`). The name in the folder must still be the opened file (same device and inode). Only then does the port truncate the file and write through the open descriptor. A refused write removes a file it created.
- The atomic write (canonical data) applies the same checks after it creates its temporary file (`O_CREAT`, `O_EXCL`, `O_NOFOLLOW`), again before the rename, and again after the rename. A port rename checks both folders before and after the rename.
- The exclusive create (`writeNewFile`: discovery and design records, evidence copies, and the design file) applies the same checks after its `O_CREAT`, `O_EXCL`, `O_NOFOLLOW` open, and removes its file when a check fails. The atomic symlink put (a promotion rollback) checks its folder before and after the rename, and `remove` checks its folder before it unlinks. The canonical-data port has no write in place: only intake output gets the in-place writer.
- Cleanup removes only what the same call or command created. A failed exclusive create, atomic write, symlink put, or in-place write removes its own new entry only when the folder path still names the folder it created the entry in (device and inode, taken right after the create) and the entry is still the one it made (device and inode, and file or link). When either changed, nothing is removed, and the refusal (exit 3) names the entry left in place. An exclusive create is complete only after its close succeeds; a failed close removes the new file. Discovery lists a record file or folder for its cleanup only after it created it, so a file another process put in the reserved folder is never removed.
- `intake convert` and `intake index` do not undo (W1 R7 P9 intake JSON review round 2, PE-022): after a failed write they remove or put back nothing, with or without `--json`, as the Go tool did. An undo that deletes from outside the writer could delete a file or folder that another program put at the same path between the write and the delete. With `--json`, the envelope names what stayed, and that list comes only from the write operations themselves, never from a lookup before or after a write: each `mkdir` of a folder level that succeeds made that folder (one level at a time, not recursive), and the in-place writer says whether it created the file, changed the entry that was there, or left the name untouched, also when the write or the close fails after the open. So a file or folder of another program is never listed as the run's own, and never deleted. Each listed path is what the run made or changed at that time. Another program can change or replace that path after the run wrote it, so a listed path is not proof that BuildOS owns the entry that is there now: each diagnostic says what the run did then, and tells the operator to look at the entry before removing anything (final check, finding 4). When the writer removed a link at the name and a later step failed, the entry names the link to make again; the file the link pointed to is not changed (finding 3). Two spellings of one file on a case-insensitive volume are one entry: the record compares the identity (device and inode) that the writer's own `fstat` after the open gives, with no other lookup (finding 5). The in-place writer's own cleanup of a new file after a failed check (the bullet above) is unchanged.
- Windows: Node opens a folder for writing, where Go fails with `EISDIR`. The in-place writer and its preflight fail with Go's `open <path>: is a directory` before the open.
- Before the first write of an intake command, every destination is checked: its folder, and, when the file exists, its type, link count, and containment. A refused command leaves no new file.
- `test/fs-port.test.ts` swaps the folder for a symlink to an outside folder between the checks and the open (and the rename), through a test-only hook, and shows that each write is refused and that nothing lands outside the root.

### `buildos init`: Shared Files

`buildos init` writes only inside the project folder and has no `--allow-outside-root`. It reads, changes, and writes back three user files at the project root: `AGENTS.md`, `CLAUDE.md`, and `.gitignore` (PRD 20 Project Initialization and Adoption). It changes only its own section and keeps every other byte; a rerun in a project that BuildOS already set up only refreshes a section that is there, and reports every other shared file with the reason it was not changed. Before any write of any kind (Make Docs included), it checks each of them: each file is read once per plan, from one open that is checked against the entry at the name, with a hard bound (`readFileLimited`; a file over 4 MiB, `SHARED_FILE_MAX_BYTES`, is not read), a file saved as UTF-16 or UTF-32 or holding a zero byte is not changed, and a link is never read or written through. A link stays as it is only when the operating system resolves it to another of the three files in the same folder (the same entry); any other link, inside or outside the root or dangling, stops the command (exit 10), so a user's link is never replaced by a regular file. The manifest and every file or link that an adoption replaces are read the same way, before Make Docs runs. A router file that BuildOS may not read stops only an operation that needs its text; for the Make Docs question its owner is then unknown, and it counts as one Make Docs did not write.

The proof that a section is BuildOS's is its integrity line, never where it sits. BuildOS writes `<!-- buildos:section v1 sha256=<hex> -->` (`# buildos:section v1 sha256=<hex>` in `.gitignore`) as the first line inside its section; the SHA-256 covers the exact text up to the end line, with each CRLF read as LF. BuildOS replaces a section only when that line is there and the hash matches, so it replaces only bytes that it wrote and that no one changed. A pair of marker lines without a valid integrity line is never replaced and never deleted: inside a code block, raw HTML block, or HTML comment it is the user's example, and outside every such region the command stops (exit 10) and names the file and line. More than one valid section, or marker lines outside every region that are not one pair, also stop the command. The region scan (fenced code; `<pre>`, `<script>`, `<style>`, and `<textarea>` opened anywhere in a line outside code spans and closed only by their own closing tag; HTML comments opened anywhere in a line and closed only by `-->`) is a second line of defense: when it is wrong, BuildOS still only adds bytes or stops, never changes or removes a byte of the user's. A file with no marker lines that ends inside a region that is never closed gets the section at its start instead of its end. A line ends at LF or CRLF only. A bare CR is text, never a line break and never marker padding, so BuildOS never drops it; a file whose buildos lines appear only when a bare CR is read as a line break stops the command before any write (exit 10). A section whose text is already current is not written, so it keeps every byte. A begin line inside a region starts an example that runs through the next end line. `test/init-review.test.ts` checks the section rules on 4,000 generated files, and `test/init-review-4.test.ts` checks the bare-CR rule on 3,000 generated files with a valid section. The init core loads no crypto module: it hashes through a port (`src/core/shared/hash-port.ts`) that the CLI passes in.

### `buildos init`: Checks Before Any Write

A file that BuildOS would replace (a shared file that gets a section, or a Go-era wrapper or skill file, also a wrapper link that itself has more than one hard link) and that has more than one hard link stops the command before Make Docs runs (exit 10): the replace writes a new file and renames it over the name, which would split the name from the other names silently. The link count is part of what the write checks again right before the rename.

Before Make Docs runs, `buildos init` also checks that every folder it writes in allows a new entry (exit 5 when not). The check looks at the folder the create or rename acts in, never through a link in it. On macOS and Linux it is `access(W_OK | X_OK)`. No probe file is written. Windows has a limit here (see [Known Limits and Out of Scope](#known-limits-and-out-of-scope)).

Each replace passes what it expects to the port: the snapshot read before Make Docs ran (a file's bytes, permission bits, identity, and hard link count, or a link's text, identity, and its own permission bits where the operating system keeps them). After Make Docs ran, the second read of the folder must see every path BuildOS will write as the first read saw it (missing, a folder, or the same file or link); a path that appeared, went away, or changed stops the run before any write (exit 10), with the Make Docs result. Only the three shared files are read anew, because Make Docs may create or change them. An identity is the device and inode (the Windows file ID), kept as a 64-bit value; a file system that reports an inode of 0 gives no identity, and every check by identity then declines (also the port's lower-level checks of folders, opened files, and its own new entries, and the version helper's manifest read). The port compares the snapshot, with a bounded read and no link followed, as the last step before the rename, after the temporary file is written and closed. So an editor save or a `chmod` at any earlier time stops the run (exit 10), and the change stays. A shared file the plan keeps as it is, and a kept link, are checked again before the run reports success. The write keeps the file's full permission bits (setuid, setgid, sticky). An adoption keeps a replaced file's own permission bits and adds the owner-execute bit, so the wrapper runs.

### `buildos init`: Journal and Undo

Every step is journaled with the identity (device and inode, or the Windows file ID) of the entry it made, and for a file the bytes and permission bits it wrote; for a replaced entry also what was there before (a file's bytes and mode, or a link's text and mode). A write that took effect and then failed in a later part (the parent folder flush after the rename) reports the entry it committed, so it is journaled and undone too. A failure undoes the journal in reverse: a replaced entry gets its earlier file or link back, and a created entry is removed, each only when the entry still has exactly the identity, bytes, and permission bits this run wrote (the port checks them right before the unlink or rename). A later change by the user, also a save in place that keeps the identity, is kept. Each path that cannot be put back, and each temporary file a failed write could not remove, is listed with its exact path in the human and JSON output; the run then exits 10 with `write_status` `partially_applied`. The list tells a real leftover (`state` `left`) from an earlier file that BuildOS did put back but whose save to disk it could not confirm (`state` `unsure`, the folder flush after the rename failed); a created entry that is already gone is not listed, because the path is as it was; and a folder that BuildOS made but could not read back is journaled and listed, never forgotten. The undo has limits (see [Known Limits and Out of Scope](#known-limits-and-out-of-scope)).

## Known Limits and Out of Scope

These are the limits of the guarantees above. Each is tracked in the W1 R7 evidence report.

Threat model: BuildOS treats every input file as untrusted. A local process that can already change the project folder while a BuildOS command runs is outside the threat model. So are a compromised Node.js, npm, or operating system.

- Time-of-check windows. Node has no `openat`, no `renameat2` with an expected inode, and no Windows equivalent, so these windows stay open; closing them needs operating-system support that Node does not offer. (1) A process that swaps a folder out of the project before a bounded read's open, and swaps it back and out again timed exactly around each check after the open, can still make BuildOS read one outside file. A swap that stays in place, or that is undone once, is always refused, because the read checks the folder and then the name after the open. (2) After a rename, the port can only report a folder swap (exit 3), not undo it. (3) In `buildos init`, a change made in the short time between the port's last check of a destination and the rename itself is not seen, and that change is replaced. (4) The same short window lies between the identity check and the unlink or rename of an undo step.
- Crash or power loss. The `buildos init` undo runs in the same process, so a crash or power loss in the middle of a run is not undone. Each single write is still atomic: a file is either the old one or the new one.
- Extended ACLs and extended attributes (follow-up F-P6-01). A replace writes a new file and renames it over the old one, so the new file keeps the POSIX permission bits (BuildOS sets them) but not the old file's extended ACLs (for example a macOS deny-write entry) or extended attributes. Node.js has no API to read or copy them, and BuildOS starts no ACL tool. Writing in place under a checked handle would keep them, but a crash in the middle of such a write leaves a half-written user file, which breaks the promise that a write is atomic and that a failed run restores every byte, so BuildOS keeps the rename. A user who relies on an ACL on `AGENTS.md`, `CLAUDE.md`, `.gitignore`, or a Go-era wrapper should set it again after `buildos init`.
- Windows folder permission check. On Windows, Node.js has no check of a folder's access rules (ACLs): `fs.access` there only looks at the read-only attribute, which Windows ignores on folders. So on Windows `buildos init` checks only a folder's existence, type, and place inside the project before it writes. A folder that denies the write is found only by the write itself, after Make Docs ran; the run is then undone and reported with the Make Docs result (exit 5).
- Windows hard link count. The hard link check uses the count that Node.js reports for NTFS. A file system without hard links (FAT, exFAT) and some network shares report one link, so there the check cannot see a link.
- Windows command line limit. Command Prompt takes at most 8,191 characters on one command line. The `npx` fallback on Windows starts `npx.cmd` through `cmd.exe`, so before it starts, the helper checks the `cmd.exe` line and the line that npm's `npx.cmd` builds from it (twice the `npx.cmd` path, 600 characters for npm's own paths, and the arguments). The 600 characters are an estimate: npm's `npx.cmd` takes its `npx-cli.js` path from `npm prefix -g`, which the helper cannot know without starting a program, so a line close to the limit can be refused although it fits (follow-up F-P8-08). When either is longer than 8,191 characters, the wrapper starts nothing, prints one plain message that names the limit, and exits 2. Shorter arguments work, and so does a local install of the pinned version, which starts with Node.js directly and has no such limit.
- Windows wrappers and shown commands. Command Prompt reads `%*` as one piece of text, so an argument that the user typed with an escaped `&`, `|`, `<`, or `>` outside quotes is split there, as with every npm `.cmd` shim. For the same reason, an argument with an odd number of double quotes (`"`) changes the quote state for the rest of that text, so a later argument with `&`, `|`, `<`, `>`, or `^` is read as a command character; put such an argument last, or run `npx` directly. An argument with an even number of double quotes, an empty argument, and a folder name with `%TEMP%` in it pass unchanged (`test/wrappers.test.ts`, Windows only). The commands that `buildos init` shows on Windows are for Command Prompt with its default settings: with delayed expansion on (`cmd /v:on`), a `!` in a folder name in such a command would still be read as a variable, and no one spelling of `!` works both with it on and off. BuildOS shows no PowerShell form.
- pdf.js and one very long string. pdf.js reads one text string of a content stream whole, so a single string of tens of millions of characters (which a small compressed PDF can hold) can exhaust a 256 MiB heap inside pdf.js before the text budget sees it. With Node's default heap (checked on macOS arm64, a 68 MB PDF with one 68-million-character string), it fails at the text budget, exit 1, after 16 s.
- Findings budget of `buildos validate` (follow-up F-P7-05). The one listing of `.os/templates/` is read whole and does not check the findings budget.
- What the deny-list check does not find: look-alike characters (homoglyphs) that NFKC does not fold, such as a Cyrillic letter in place of a Latin one; text drawn in the pixels of an image (only names and metadata are read); compressed data of any kind not named above (for example a compressed EXIF block in another format); a term split across two JPEG segments; text in a PDF stream that is not Flate-compressed or that a font maps to other characters; a term split across two table cells or two text boxes, or across two sibling elements of generic XML whose parent has no text of its own; a name encoded twice (for example `&amp;amp;`) or with an HTML named reference other than the six it reads (follow-up F-P7-07); content past three archive levels (counted as not fully scanned); and git history.
- Git history. The check scans the current files, not old commits. The public repository has one clean commit as its first commit, and the deny-list check with the real list runs on that tree before the first push (Owner Settings for Releases, step 5). Only `main` is pushed, and the remote is checked to hold one commit, one branch, and no tag (steps 6 and 16). The old history, which holds client text that was removed and two removed Go binaries with a personal build path, stays only in the private archive repository `brucewaynedecoy/build-os-archive` (owner decision of 2026-11-25). Commit hashes in these docs from before the public repository (for example the frozen Go baseline `263f5ca`) name commits of the earlier history, which exists only in the private archive repository `brucewaynedecoy/build-os-archive`: the public repository starts from one clean commit (owner decision of 2026-11-25).
- Skill scripts. From `0.2.0` the package ships no skill script: `buildos extract bulk`, `buildos fitgap`, and `buildos export azure-boards` replace the three scripts of `0.1.0` with the rules above, and the skills call them (W1 R7 P9 Stage 3). A project that pins `0.1.0` still has those scripts in `.os/skills/`; BuildOS never runs them, and an agent may run them at the user's request with the user's own Python or Node.js. The `capability-matrix` skill still tells the agent to write and run its own Python tool (F-P9-04); BuildOS never runs it.
- `extract bulk` lock file. Node has no file lock, so a command that crashes or is killed leaves `extractions/staging/.buildos-extract-bulk-stage.lock` or `.buildos-extract-bulk-publish.lock` behind, and that stops the next command also for a single user. The lock file records the process ID, the host, and the time; the message names them and says how to check that the process is gone (`ps -p <pid>`, or `tasklist /FI "PID eq <pid>"` on Windows) before deleting the file. BuildOS does not clear a lock by itself: a process ID can be reused (quickly on Windows), and a lock in a shared folder can belong to another host or container, so no check is reliable on all three systems. Two commands that start at the same moment cannot both take the lock (an exclusive create).
- CSV formula prefixes. `buildos export azure-boards` keeps a leading `=`, `+`, `-`, or `@` in a CSV field, as its original script did, so the file imports into Azure Boards unchanged (import parity). A spreadsheet program that opens the CSV may read such a field as a formula. Open the file with Azure Boards' CSV import, or in a spreadsheet only from a trusted manifest; to inspect a file from a manifest that is not trusted, read it as plain text or with a CSV reader that treats every cell as text. The skill's `SKILL.md` and its CSV contract say this (the skill's own inspection step uses such a reader), and the skill tells the agent to say it when it delivers a CSV (W1 R7 P9 Stage 3, follow-ups P9-R1-F1 and F-P9-02).
- `fitgap` workbook text. Text that is exactly an Excel error token (such as `#N/A`) is written as text, not as an error value; text that looks like Office Open XML's own escape (`_xHHHH_`) is written escaped, so Excel shows it as typed. One rule covers every part (review round 2, P9-R2-13): free text (cells, shared strings, the document title) loses each character XML 1.0 cannot hold (a control character other than tab, line feed, and carriage return, as openpyxl dropped them; and U+FFFE, U+FFFF, or a lone surrogate, which stderr reports), and a model code that would put such a character into a sheet name, a link, or a column heading stops the command before anything is built (exit 4); the writer stops on any such character that still reached it (divergence SD-19).
- Out of scope for this release: an MCP server, standalone executables with Node embedded, `buildos update`, `buildos uninstall`, project sync, and OCR for scanned PDFs.

## Reporting a Vulnerability

Do not open a public issue or pull request for a security problem. Report it privately through GitHub private vulnerability reporting: `https://github.com/brucewaynedecoy/build-os/security/advisories/new` (the **Security** tab of the repository, then **Report a vulnerability**). Include the BuildOS version (`buildos version --json`), the operating system, the command you ran, and what you saw.

The maintainer reviews reports for the current npm release and the `main` branch, and coordinates any fix and disclosure through the private advisory. There is no promised response time or release date. A fix ships as a new release; see [Rollback by Version Pin](#rollback-by-version-pin) to move off an affected version.

## Admission Checklist

Every new outside package must pass this checklist in the change that adds it. The same change updates this document and, for bundled code, `THIRD_PARTY_NOTICES.md`.

- [ ] Node has no built-in module that can do the job. The reason is written down.
- [ ] The package is widely used and actively maintained. Evidence: download count, recent release, open-issue response.
- [ ] The license is MIT, Apache-2.0, BSD, or ISC, for the package and for every transitive package.
- [ ] The package has few or no dependencies. The transitive count is recorded.
- [ ] The version is exact in `package.json` and recorded in `package-lock.json`.
- [ ] No install script. The only exception is `esbuild` 0.28.2; see [Install-Script Exception](#install-script-exception). A package with an install script cannot be admitted without a new owner decision recorded in PRD 20.
- [ ] `npm audit --audit-level=high` and the OSV scan pass with no high or critical finding.
- [ ] A runtime package is bundled by esbuild and is not a `dependencies` entry.
- [ ] This document lists the package in the right section and in the inventory, the SBOM check passes, and the scan record is current.
